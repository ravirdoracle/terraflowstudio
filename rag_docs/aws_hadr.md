# Oracle AI Database@AWS — Business Continuity (HADR)

Source: Oracle Cloud Infrastructure Documentation — database-at-aws-exadata HADR
Source URL: https://docs.oracle.com/en-us/iaas/Content/database-at-aws-exadata-awsbc/awsbc-business-continuity-hadr.html

---

## Overview

HADR for Oracle AI Database@AWS covers Oracle Data Guard configuration across availability zones and regions for:
- Oracle Exadata Database Service on Dedicated Infrastructure
- Oracle Autonomous AI Database on Dedicated Infrastructure (documentation pending)

Traffic routed via the OCI network (VCNs auto-created during Oracle AI Database@AWS deployment).

---

## Part 1: Prerequisites — Network Connectivity

### Multi-AZ Configuration (Same Region, Different AZs)

**Architecture:**
- Primary Exadata VM Cluster: Primary AZ, VCN 1
- Standby Exadata VM Cluster: Standby AZ, VCN 2
- Application VPC peered with ODB Network 1 and ODB Network 2

**Example CIDRs:**
- Primary Client Subnet: `10.10.1.0/24`
- Standby Client Subnet: `10.20.1.0/24`

#### Primary Zone Configuration

**Step 1: Navigate to Primary VCN**
```
AWS Console → Oracle AI Database@AWS → Exadata VM Cluster → select cluster → OCI Console
→ Networking → Virtual Cloud Network
```

**Step 2: Create Local Peering Gateway**
1. Virtual Cloud Network details → Gateways tab → Local Peering Gateways → Create Local Peering Gateway
2. Name: `Primary-LPG`
3. **Record Primary-LPG OCID**

**Step 3: Update NSG Rules (Primary)**
Security tab → Network Security Groups → VM Cluster NSG → Security rules → Add Rules:

| Property | Value |
|---|---|
| Direction | Ingress |
| Source CIDR | `10.20.1.0/24` (standby) |
| Protocol | TCP |
| Destination Port | 1521 |
| Description | Allow Data Guard from Standby |

**Step 4: Add Route Rule (Primary)**
Routing tab → Default Route Table → Add Route Rules:

| Property | Value |
|---|---|
| Route Rule Type | Local Peering Gateway |
| Destination CIDR | `10.20.1.0/24` |
| Target LPG | Primary-LPG |

#### Standby Zone Configuration

**Step 1: Create Local Peering Gateway**
1. OCI Console → Standby VM Cluster → Network → Virtual Cloud Network → Gateways tab
2. Create `Standby-LPG`

**Step 2: Establish Peering**
1. Local Peering Gateways → Standby-LPG → three dots → Establish Peering Connection
2. Select **Enter Local Peering Gateway OCID** → paste Primary-LPG OCID
3. Click Establish Peering Connection

**Step 3: Update NSG Rules (Standby)**
Ingress from `10.10.1.0/24`, TCP 1521

**Step 4: Add Route Rule (Standby)**
Local Peering Gateway, Destination `10.10.1.0/24`, Target: Standby-LPG

**Test Connectivity:**
```bash
ping 10.20.1.0        # Primary to Standby
ping 10.10.1.0        # Standby to Primary
ssh user@standby_instance
```

### Cross-Region Configuration

Uses Dynamic Routing Gateways (DRG) + Remote Peering Connections (RPC) + hub VCNs.

**Example CIDRs:**

| Component | CIDR | Notes |
|---|---|---|
| Primary Client Subnet | `10.10.1.0/24` | Auto-created |
| Primary Hub VCN | `10.15.0.0/24` | Created manually |
| Standby Client Subnet | `10.30.1.0/24` | Auto-created |
| Standby Hub VCN | `10.16.0.0/24` | Created manually |

Plan hub CIDRs to avoid overlap (min `/28`). Review Remote Peering Connection Count service limits.

#### Primary Region Configuration

1. **Create Hub VCN:** `primary-hub-vcn`, CIDR `10.15.0.0/24`

2. **Create LPGs:**
   - `primary-hub-lpg` in Primary-Hub VCN
   - `primary-lpg` in Primary VM Cluster VCN

3. **Establish LPG Peering:** primary-lpg → Browse Below → Primary-Hub VCN → primary-hub-lpg

4. **Create DRG:** `Primary-hub-drg`
   ```
   OCI Console → Networking → Customer Connectivity → Dynamic Routing Gateway → Create
   ```

5. **Create route table `primary_hub_transit_drg`** in Primary-Hub VCN:
   - Target: Local Peering Gateway
   - Dest CIDR: `10.10.1.0/24` (Primary Client Subnet)
   - Target LPG: primary-hub-lpg

6. **Attach DRG to Primary-Hub VCN** with route table `primary_hub_transit_drg`

7. **Create route table `primary_hub_transit_lpg`** in Primary-Hub VCN:
   - Target: Dynamic Routing Gateway
   - Dest CIDR: `10.30.1.0/24` (Standby Client Subnet)
   - Target DRG: Primary-hub-drg

8. **Associate `primary_hub_transit_lpg`** to primary-hub-lpg

9. **Edit DRG attachment:** select Autogenerated DRG Route Table for RPC, VC, IPSec attachments

10. **Validate DRG route table:**
    - Enable import route distribution = ON
    - Import route distribution = Autogenerated Import Route Distribution for ALL routes

11. **Create Remote Peering Connection** on Primary-Hub-DRG → **record Primary RPC OCID**

12. **Update Primary VCN default route table:**
    - Target: Local Peering Gateway
    - Dest CIDR: `10.30.1.0/24`
    - Target LPG: primary-lpg

13. **Update Primary NSG:** Ingress from `10.30.1.0/24`, TCP 1521 (optionally port 22 for SSH)

#### Standby Region Configuration

1. **Create Hub VCN:** `standby-hub-vcn`, CIDR `10.16.0.0/24`

2. **Create LPGs:**
   - `standby-hub-lpg` in Standby-Hub VCN
   - `standby-lpg` in Standby VM Cluster VCN

3. **Establish LPG Peering:** standby-lpg → Browse Below → Standby-Hub VCN → standby-hub-lpg

4. **Create DRG:** `standby-hub-drg`

5. **Create route table `standby_hub_transit_drg`** in Standby-Hub VCN:
   - Target: Local Peering Gateway
   - Dest CIDR: `10.30.1.0/24` (Standby Client Subnet)
   - Target LPG: standby-hub-lpg

6. **Attach DRG to Standby-Hub VCN** with route table `standby_hub_transit_drg`

7. **Create route table `standby_hub_transit_lpg`** in Standby-Hub VCN:
   - Target: Dynamic Routing Gateway
   - Dest CIDR: `10.10.1.0/24` (Primary Client Subnet)
   - Target DRG: standby-hub-drg

8. **Associate `standby_hub_transit_lpg`** to standby-hub-lpg

9. **Edit DRG attachment:** Autogenerated DRG Route Table for RPC, VC, IPSec

10. **Validate DRG route table:** Enable import route distribution = ALL routes

11. **Create Remote Peering Connection** on Standby-Hub-DRG

12. **Establish Cross-Region Connection:**
    - Region: Primary region
    - Remote peering connection OCID: paste **Primary RPC OCID**
    - Status "peered" = both regions connected

13. **Update Standby VCN default route table:**
    - Target: Local Peering Gateway
    - Dest CIDR: `10.10.1.0/24`
    - Target LPG: standby-lpg

14. **Update Standby NSG:** Ingress from `10.10.1.0/24`, TCP 1521 (optionally port 22)

**Network Components Summary:**

| Component | Multi-AZ | Cross-Region |
|---|---|---|
| VCNs | 2 | 4 (2 per region incl. hubs) |
| Local Peering Gateways | 2 | 4 |
| Dynamic Routing Gateways | 0 | 2 |
| Remote Peering Connections | 0 | 2 |
| Route Tables | 2 | 6+ |
| Data Guard Port | TCP 1521 | TCP 1521 |

## Part 2: Exadata Database — Data Guard Configuration

### Access Path

AWS Console → Oracle AI Database@AWS → Exadata VM Cluster → select cluster → OCI Console → Oracle AI Database → Exadata Database Service on Dedicated Infrastructure → Exadata VM Clusters → select cluster → Databases tab → select DB → **Data Guard Associations** tab → **Add standby**

### Configuration Parameters

| Parameter | Options / Notes |
|---|---|
| Data Guard Resource Type | New Data Guard Group or existing Association |
| Multi-AZ | Same region, different Availability Domain |
| Cross-Region | Different region than source |
| Service | Exadata Database Service on Dedicated Infrastructure |
| Data Guard Type | Data Guard or Active Data Guard (license required) |
| Protection Mode | Maximum Performance (default; **only option for cross-region**) |
| Transport Type | Async (default; **only option for cross-region**) |
| Database Home | Must match primary Oracle DB version and patches |

### Active Data Guard Features (requires Oracle ADG license)
Real-Time Query, DML Offload, Automatic Block Repair, Standby Block Change Tracking, Far Sync, Global Data Services, Application Continuity

### Database Unique Name
- Max 30 chars, alphanumeric + underscore, start with letter
- Unique across VM clusters (recommended: entire tenancy)
- **Immutable** after creation
- Auto-format: `<db_name>_<3_chars>_<region-name>`

### SID Prefix (Advanced Options → Management)
- Max 12 chars, alphanumeric, start with letter; Oracle 12.1+ only
- Defaults to first 12 chars of `db_unique_name`; **immutable** after creation
- Must be unique across primary and standby

### Password Requirements
- Administrator password must equal TDE wallet password exactly
- Mismatch: run `dbaascli` Changing Database Passwords procedure

### Precheck and Deployment
1. Click **Run Precheck** — Add Standby page closes; primary stays AVAILABLE
2. View Details → Work Requests: Succeeded or Failed
3. Resolve failures and retry
4. If succeeded → Data Guard Associations tab → **Add** → configure again → **Add**
5. Monitor progress on standby's Work Requests page

### Post-Creation State
- Primary database displays role: **Primary**
- Standby database displays role: **Standby**
- New Data Guard Group or Association created between databases

## Key Constraints

| Constraint | Value |
|---|---|
| Cross-region protection mode | Maximum Performance only |
| Cross-region transport type | Async only |
| CIDR planning | No overlapping ranges across VCNs |
| Hub VCN size | Minimum /28 |
| Far Sync | Plan hub VCN CIDR if deploying Far Sync compute |
| `db_unique_name` | Immutable after creation |
| SID prefix | Immutable after creation |
| TDE wallet password | Must match admin password |
