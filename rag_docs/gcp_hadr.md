# Oracle AI Database@Google Cloud — Business Continuity (HADR)

Source: Oracle Cloud Infrastructure Documentation — database-at-gcp HADR
Source URL: https://docs.oracle.com/en-us/iaas/Content/database-at-gcp/gcpbc-business-continuity-hadr.html

## Overview

HADR for Oracle AI Database@GCP covers Oracle Data Guard configuration across availability zones and regions for:
- Oracle Exadata Database Service on Dedicated Infrastructure
- Oracle Exadata Database Service on Exascale Infrastructure
- Oracle Autonomous AI Database (Serverless)
- Oracle Base Database Service (docs pending)

Traffic can be routed via **OCI network** or **Google Cloud network**.

---

## Part 1: Prerequisites — Network Connectivity

### Cross-Zone Data Guard

Cross-zone deploys primary and standby in different zones within the same GCP region.

**Example CIDRs:**
- Primary Client Subnet: `10.10.1.0/24`
- Standby Client Subnet: `10.20.1.0/24`

#### Option A: OCI Network (via Local Peering Gateways)

**Primary Zone:**
1. GCP Console → primary instance → **Manage in OCI**
2. OCI Console → Networking → Virtual Cloud Networks → Primary VCN → Gateways tab
3. Create Local Peering Gateway: name `Primary-LPG`, **record OCID**
4. NSG (Security tab → VM Cluster NSG → Add Rules): Ingress from `10.20.1.0/24`, TCP 1521
5. Route table (Routing tab → Default → Add Route Rules): LPG target, dest `10.20.1.0/24` → Primary-LPG

**Standby Zone:**
1. Create `Standby-LPG` in Standby VCN Gateways tab
2. Establish Peering: three dots → Establish Peering Connection → paste Primary-LPG OCID
3. NSG: Ingress from `10.10.1.0/24`, TCP 1521
4. Route table: LPG target, dest `10.10.1.0/24` → Standby-LPG

#### Option B: Google Cloud Network

**Requirement:** VPC dynamic routing mode must be **global**.

1. Primary VM Cluster NSG: Ingress from `10.20.1.0/24`, TCP 1521
2. Standby VM Cluster NSG: Ingress from `10.10.1.0/24`, TCP 1521
3. No LPGs or route tables needed — GCP VPC handles routing

### Cross-Region Data Guard

Uses DRG + RPC + hub VCNs (OCI path) or global GCP VPC (Google path).

**Example CIDRs:**
- Primary Client Subnet: `10.10.1.0/24`, Primary Hub VCN: `10.15.0.0/24`
- Standby Client Subnet: `10.30.1.0/24`, Standby Hub VCN: `10.16.0.0/24`

Plan hub VCN CIDRs to avoid overlap. Review Remote Peering Connection Count limits.

#### Option A: OCI Network

**Primary Region:**
1. Create Hub VCN: `primary-hub-vcn`, CIDR `10.15.0.0/24`
2. Create `primary-hub-lpg` (in hub) and `primary-lpg` (in Primary VM Cluster VCN)
3. Establish peering: primary-lpg → primary-hub-lpg
4. Create DRG: `Primary-hub-drg`
5. Route table `primary_hub_transit_drg`: LPG target, dest `10.10.1.0/24` → primary-hub-lpg
6. Attach DRG to hub VCN with `primary_hub_transit_drg`
7. Route table `primary_hub_transit_lpg`: DRG target, dest `10.30.1.0/24` → primary-hub-drg
8. Associate `primary_hub_transit_lpg` to primary-hub-lpg
9. Edit DRG attachment: Autogenerated DRG Route Table for RPC, VC, IPSec
10. Validate DRG route table: Enable import route distribution = ALL routes
11. Create Remote Peering Connection → **record Primary RPC OCID**
12. Update Primary VCN default route table: LPG target, dest `10.30.1.0/24` → primary-lpg
13. NSG: Ingress from `10.30.1.0/24`, TCP 1521

**Standby Region:**
1. Create Hub VCN: `standby-hub-vcn`, CIDR `10.16.0.0/24`
2. Create `standby-hub-lpg` (in hub) and `standby-lpg` (in Standby VM Cluster VCN)
3. Establish peering: standby-lpg → standby-hub-lpg
4. Create DRG: `standby-hub-drg`
5. Route table `standby_hub_transit_drg`: LPG target, dest `10.30.1.0/24` → standby-hub-lpg
6. Attach DRG to standby hub VCN
7. Route table `standby_hub_transit_lpg`: DRG target, dest `10.10.1.0/24` → standby-hub-drg
8. Associate `standby_hub_transit_lpg` to standby-hub-lpg
9. Edit DRG attachment and validate (same as primary)
10. Create Remote Peering Connection (standby-hub-drg)
11. Establish Connection: select primary region, paste **Primary RPC OCID** → status = "peered"
12. Update Standby VCN default route table: LPG target, dest `10.10.1.0/24` → standby-lpg
13. NSG: Ingress from `10.10.1.0/24`, TCP 1521

#### Option B: Google Cloud Network (Cross-Region)

**Requirements:**
- VPC dynamic routing mode: **global**
- Configure large MTU size (**8896**) to reduce packet fragmentation across regions
- Optional: request Google Cloud Interconnect VLAN bandwidth increase via support ticket

1. Primary NSG: Ingress from `10.30.1.0/24`, TCP 1521
2. Standby NSG: Ingress from `10.10.1.0/24`, TCP 1521
3. GCP VPC global routing handles cross-region traffic

## Part 2: Exadata Database — Data Guard Configuration

### Access Path

GCP Console → primary instance → **Manage in OCI** → Oracle AI Database → Exadata Database Service on Dedicated Infrastructure → Exadata VM Clusters → cluster → Databases tab → select DB → Data Guard Group tab → **Add standby**

### Configuration Parameters

| Parameter | Options / Notes |
|---|---|
| Data Guard Resource Type | New Data Guard Group or existing Association |
| Cross-Region | Select different region than source |
| Cross-Zone | Same region, different Availability Domain |
| Service | Exadata Database Service on Dedicated Infrastructure |
| Data Guard Type | Data Guard or Active Data Guard (license required) |
| Protection Mode | Maximum Performance (default; only option for cross-region) |
| Transport Type | Async (default; only option for cross-region) |
| Database Home | Must match primary Oracle DB version and patches |

### Active Data Guard Features (requires license)
Real-Time Query, DML Offload, Automatic Block Repair, Standby Block Change Tracking, Far Sync, Global Data Services, Application Continuity

### Database Unique Name
- Max 30 chars, alphanumeric + underscore, start with letter
- Unique across VM clusters (recommended: entire tenancy)
- **Immutable** after creation
- Auto-format: `<db_name>_<3_chars>_<region-name>`

### SID Prefix (Advanced Options → Management)
- Max 12 chars, alphanumeric, start with letter; Oracle 12.1+ only
- Defaults to first 12 chars of `db_unique_name`; **immutable** after creation

### Passwords
- Admin password must equal TDE wallet password
- Mismatch: run `dbaascli` Changing Database Passwords procedure

### Precheck and Deployment
1. **Run Precheck** → primary stays AVAILABLE → check Work Requests: Succeeded or Failed
2. If succeeded → Data Guard Associations tab → **Add** → configure again → **Add**

## Part 3: Exascale Database — Data Guard Configuration

Same access path as Exadata, but navigate to:
**Oracle Exadata Database Service on Exascale Infrastructure → Exadata VM Clusters → cluster → Container databases tab → select DB → Data Guard Group tab → Add standby**

All parameters identical to Exadata Data Guard (see Part 2), including:
- Cross-region: Maximum Performance + Async only
- Immutable `db_unique_name` and SID prefix
- Admin password = TDE wallet password
- Precheck required before creation

## Part 4: Autonomous AI Database (Serverless) — Disaster Recovery

### Regional Availability

| Region | Versions | Zone Config |
|---|---|---|
| US East (Ashburn) | 19c, 26ai | Dual-Zone |
| Germany Central (Frankfurt) | 19c, 26ai | Dual-Zone |
| UK South (London) | 19c, 26ai | Dual-Zone |
| Australia Southeast (Melbourne) | 19c, 26ai | Dual-Zone |
| Italy Northwest (Milan) | 19c, 26ai | Dual-Zone |
| US Midwest (Des Moines) | 19c | Single-Zone |

### Cross-Region DR Paired Regions

| Region A | Region B |
|---|---|
| us-east4 (Northern Virginia) | us-west3 (Salt Lake City) |
| europe-west2 (London) | europe-west3 (Frankfurt) |
| us-east4 (Northern Virginia) | US Midwest (Des Moines) |
| europe-west8 (Milan) | europe-west3 (Frankfurt) |

### RTO / RPO

| Metric | Value |
|---|---|
| Recovery Time Objective (RTO) | ~15 minutes |
| Recovery Point Objective (RPO) | ~1 minute |

### Constraints
- Max 1 local peer + 1 cross-region peer per paired region
- Cross-region Autonomous Data Guard incurs additional cost

### gcloud CLI Setup

```bash
# Verify/update gcloud
gcloud --version
gcloud components update

# Required: Google Cloud SDK 564.0.0+

# Set environment variables
export GCP_PROJECT_NUMBER="YOUR_PROJECT_NUMBER"
export GCP_LOCATION="YOUR_GCP_LOCATION"   # e.g., us-east4
export ADBS_NAME="YOUR_ADBS_ID"           # e.g., gi126pesc9tp1
export ADB_ID="projects/${GCP_PROJECT_NUMBER}/locations/${GCP_LOCATION}/autonomousDatabases/${ADBS_NAME}"
```

### Enable Autonomous Data Guard (Local/Cross-Zone)

```bash
# Enable ADG
gcloud oracle-database autonomous-databases update "${ADB_ID}" \
  --location="${GCP_LOCATION}" \
  --properties-local-data-guard-enabled

# Verify — look for isLocalDataGuardEnabled: true
gcloud oracle-database autonomous-databases describe "${ADB_ID}" \
  --location="${GCP_LOCATION}"

# Set max data loss limit (seconds)
gcloud oracle-database autonomous-databases update "${ADB_ID}" \
  --location="${GCP_LOCATION}" \
  --properties-local-adg-auto-failover-max-data-loss-limit-duration=60
```

### Switchover (Planned)

```bash
gcloud oracle-database autonomous-databases switchover "${ADB_ID}" \
  --location="${GCP_LOCATION}"
```

### Failover (Unplanned)

```bash
gcloud oracle-database autonomous-databases failover "${ADB_ID}" \
  --location="${GCP_LOCATION}"
```

### Disable ADG

```bash
gcloud oracle-database autonomous-databases update "${ADB_ID}" \
  --location="${GCP_LOCATION}" \
  --no-properties-local-data-guard-enabled
```

### Cross-Region DR Setup (Console)

1. GCP Console → Oracle AI Database@GCP → Autonomous AI Database → select DB
2. **Disaster recovery** tab → **+ Create**
3. Select paired region
4. Select DR type: Backup-based or Autonomous Data Guard
5. Configure network: ODB Network + Client subnet
6. Optional: Private IP address, hostname prefix (letters/numbers, max 63 chars)
7. **Save**

Network settings are modifiable post-deployment via OCI console.

|---|---|---|---|

| Active Data Guard | Optional | — | Requires ADG license |
| Autonomous DR RTO/RPO | — | — | 15 min / 1 min |
