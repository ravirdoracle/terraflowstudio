# Oracle AI Database@Azure — Business Continuity (HADR)

## Overview

HADR for Oracle AI Database@Azure covers Data Guard configuration across availability zones and regions for:
- Oracle Exadata Database Service on Dedicated Infrastructure
- Oracle Exadata Database Service on Exascale Infrastructure
- Oracle Base Database Service
- Oracle Autonomous AI Database (Serverless and Dedicated)

---

## Part 1: Prerequisites — Network Connectivity

### Cross-Zone Data Guard (Same Region, Different AZs)

Recommended for production: deploy across two Azure Availability Zones. Traffic routed via OCI network using Local Peering Gateways (LPGs).

**Example CIDRs:**
- Primary VCN: `10.10.0.0/16`, Client Subnet: `10.10.1.0/24`
- Standby VCN: `10.20.0.0/16`, Client Subnet: `10.20.1.0/24`

#### Primary Zone Configuration

1. OCI Console → Networking → Virtual Cloud Networks → Select Primary VCN → Gateways tab
2. Create Local Peering Gateway: name `Primary-LPG`, record its OCID
3. NSG (Security tab → Network Security Groups → VM Cluster NSG → Security rules → Add Rules):
   - Ingress, CIDR `10.20.1.0/24`, TCP, port 1521 (Data Guard from Standby)
4. Route table (Routing tab → Default Route Table → Add Route Rules):
   - Type: Local Peering Gateway, Destination: `10.20.1.0/24`, Target: Primary-LPG

#### Standby Zone Configuration

1. Create Standby-LPG in Standby VCN Gateways tab
2. Establish Peering: three dots → Establish Peering Connection → paste Primary-LPG OCID
3. NSG: Ingress from `10.10.1.0/24`, TCP port 1521
4. Route table: Local Peering Gateway, Destination `10.10.1.0/24`, Target: Standby-LPG

### Cross-Region Data Guard

Uses Dynamic Routing Gateways (DRG) + Remote Peering Connections (RPC) + hub VCNs.

**Example CIDRs:**
- Primary Client Subnet: `10.10.1.0/24`, Primary Hub VCN: `10.15.0.0/24`
- Standby Client Subnet: `10.30.1.0/24`, Standby Hub VCN: `10.16.0.0/24`

Plan hub VCN CIDRs to avoid overlap (minimum `/28`). Review Remote Peering Connection Count limits.

#### Primary Region Steps

1. Create Hub VCN: `primary-hub-vcn`, CIDR `10.15.0.0/24`
2. Create LPGs: `primary-hub-lpg` (in hub) and `primary-lpg` (in Primary VM Cluster VCN)
3. Establish peering: primary-lpg → primary-hub-lpg (Browse Below)
4. Create DRG: `primary-hub-drg`
5. Create route table `primary_hub_transit_drg`: LPG target, dest `10.10.1.0/24` → primary-hub-lpg
6. Attach DRG to hub VCN with route table `primary_hub_transit_drg`
7. Create route table `primary_hub_transit_lpg`: DRG target, dest `10.30.1.0/24` → primary-hub-drg
8. Associate `primary_hub_transit_lpg` to primary-hub-lpg
9. Edit DRG attachment: select Autogenerated DRG Route Table for RPC, VC, IPSec attachments
10. Validate DRG route table: Enable import route distribution = ALL routes
11. Create Remote Peering Connection on primary-hub-drg → **record Primary RPC OCID**
12. Update Primary VCN default route table: LPG target, dest `10.30.1.0/24` → primary-lpg
13. NSG: Ingress from `10.30.1.0/24`, TCP port 1521

#### Standby Region Steps

1. Create Hub VCN: `standby-hub-vcn`, CIDR `10.16.0.0/24`
2. Create LPGs: `standby-hub-lpg` (in hub) and `standby-lpg` (in Standby VM Cluster VCN)
3. Establish peering: standby-lpg → standby-hub-lpg (Browse Below)
4. Create DRG: `standby-hub-drg`
5. Create route table `standby_hub_transit_drg`: LPG target, dest `10.30.1.0/24` → standby-hub-lpg
6. Attach DRG to standby hub VCN with route table `standby_hub_transit_drg`
7. Create route table `standby_hub_transit_lpg`: DRG target, dest `10.10.1.0/24` → standby-hub-drg
8. Associate `standby_hub_transit_lpg` to standby-hub-lpg
9. Edit DRG attachment: select Autogenerated DRG Route Table for RPC, VC, IPSec attachments
10. Validate DRG route table: Enable import route distribution = ALL routes
11. Create Remote Peering Connection on standby-hub-drg
12. Establish Connection: select primary region, paste **Primary RPC OCID** → peering status = "peered"
13. Update Standby VCN default route table: LPG target, dest `10.10.1.0/24` → standby-lpg
14. NSG: Ingress from `10.10.1.0/24`, TCP port 1521

## Part 2: Exadata Database — Data Guard Configuration

### Access Path

Azure Portal → primary instance → **Go to OCI** → Oracle AI Database → Exadata Database Service on Dedicated Infrastructure → Exadata VM Clusters → select cluster → Databases tab → select database → Data Guard Group tab → **Add standby**

### Key Configuration Options

| Parameter | Options / Notes |
|---|---|
| Data Guard Resource Type | New Data Guard Group or existing Data Guard Association |
| Cross-Region | Select different region than source |
| Cross-Zone | Same region, different Availability Domain |
| Service | Exadata Database Service on Dedicated Infrastructure |
| Data Guard Type | Data Guard (standard) or Active Data Guard (requires ADG license) |
| Protection Mode | Maximum Performance (default; only option for cross-region) |
| Transport Type | Async (default; only option for cross-region) |
| Database Home | Must run same Oracle DB version and patches as primary |

### Active Data Guard Features (requires license)
Real-Time Query, DML Offload, Automatic Block Repair, Standby Block Change Tracking, Far Sync, Global Data Services, Application Continuity

### Database Unique Name
- Max 30 chars, alphanumeric + underscore, start with letter
- Unique across VM clusters (recommended: unique across tenancy)
- **Immutable** after creation
- Auto-format if blank: `<db_name>_<3_chars>_<region-name>`

### SID Prefix (Advanced Options → Management)
- Max 12 chars, alphanumeric, start with letter
- Unique in VM cluster and across primary/standby
- Defaults to first 12 chars of `db_unique_name`
- **Immutable** after creation
- Oracle 12.1+ only

### Password Requirements
- Administrator password must equal TDE wallet password
- If they differ, run Changing Database Passwords procedure (`dbaascli`)

### Precheck
1. Click **Run Precheck** — page closes, primary stays AVAILABLE
2. View Details → Work Requests: check Succeeded or Failed
3. If succeeded → Data Guard Associations tab → **Add** → repeat config → **Add**

## Part 3: Base Database — Data Guard Configuration

### NSG Rule (Primary VCN first)

| Property | Value |
|---|---|
| Direction | Ingress |
| Stateless | No (stateful) |
| Source CIDR | Standby client subnet (e.g., `10.6.0.0/24`) |
| Protocol | TCP |
| Destination Port | 1521 |

### Enable Data Guard Steps

OCI Console → Oracle AI Database → Oracle Base Database Service → DB Systems → select DB → **Data Guard Associations** tab → **Enable Data Guard**

| Parameter | Notes |
|---|---|
| DB system name | Descriptive standby name |
| Multicloud partner region | Standby region |
| Partner availability zone | Standby AZ |
| Shape | X86 only (Base AI Database@Azure) |
| License | License included or BYOL |
| Data Guard option | Data Guard |
| Protection mode | Validate for service/region pair |
| Transport type | Async |
| Database home | Match primary software image/version |
| SYS password | Password for SYS user |

**Post-configuration:** Enable **Fast-Start Failover** by installing Data Guard Observer on a separate VM.

**Version requirements:**
- Primary and standby must run identical Oracle DB versions and editions
- For 26ai: same major release required; standby may be higher minor version

## Part 4: Autonomous AI Database (Serverless) — Disaster Recovery

### DR Types

| Type | Details |
|---|---|
| Backup-Based DR | Standard backup/recovery |
| Autonomous Data Guard | Standby in separate AZ or region; RPO ~1 min; supports auto-failover |

### Peer Limits

| Deployment Mode | Local Peers | Cross-Region Peers |
|---|---|---|
| Secure access from everywhere | 1 | N/A |
| Secure access from allowed IPs | 1 | N/A |
| Managed private virtual network | 1 | 1 per remote paired region |

### Azure Portal — Add DR

1. Azure Portal → Oracle AI Database@Azure → Autonomous AI Database → select DB
2. Settings → **Disaster recovery** → **Add**
3. Region, Resource group, Name (alphanumeric, starts with letter, max 30 chars)
4. DR type: Backup-based or Autonomous Data Guard
5. Networking: Virtual network and Subnet
6. Optional: Enable cross-region backup replication
7. Next → Review + create → Create

### Azure Portal — Switchover (planned, zero data loss)

Settings → Disaster recovery → **Switchover** → select Peer autonomous database → type `switchover` → Submit

### Azure CLI Commands

```bash
# Change DR type (Adg or BackupBased)
az oracle-database autonomous-database change-disaster-recovery-configuration \
    --resource-group demo-rg-nrj \
    --autonomousdatabasename demoadbnrj \
    --disaster-recovery-type Adg \
    --is-replicate-automatic-backups False

# Switchover
az oracle-database autonomous-database switchover \
    --ids "/subscriptions/.../providers/Oracle.Database/autonomousDatabases/demoadb01"

# Failover
az oracle-database autonomous-database failover \
    --autonomousdatabasename demoadbnrj \
    --resource-group demo-rg-nrj \
    --peer-db-id demoadbnrj
```

**Note:** Create DR only via Azure Portal (not CLI). Cross-region DR only via Portal or CLI.

### Cross-Region DR Pairs (Azure Regions)

**North America:**
- East US ↔ Brazil South, Canada Central, Central US, France Central, North Central US, Southeast Asia, West Europe, West US, West US 3
- West US ↔ East US, West US 2, West US 3

**Europe:**

- Germany West Central ↔ France Central, Spain Central, Sweden Central

**APAC:**

- Australia East ↔ Australia Southeast, UK South

## Summary

| Config | Scope | Gateway Types | Supported Modes |
|---|---|---|---|
| Cross-Zone | Same region, different AZ | LPG | All protection modes |
| Cross-Region | Different regions | DRG + RPC + LPG via hub VCNs | Maximum Performance + Async only |
| Data Guard port | Both | — | TCP 1521 |
| Active Data Guard | Optional | — | Requires ADG license |
